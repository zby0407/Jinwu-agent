# Solar-Cycle Co-Scientist 设计文档

## 1. 项目定位

项目名称：

**Solar-Cycle Co-Scientist：基于 Pi Agent 的太阳活动周假设生成、自动实验与证据推理系统**

对应竞赛方向：

**金乌·太阳物理建模迭代与假设生成 / 太阳活动周起源探秘**

本项目面向太阳活动约 11 年周期的起源、演化和预测问题。系统不是单纯训练一个预测模型，也不是只做太阳物理数据可视化，而是把 Pi Agent 设计成一个多智能体科研流程：它能够把开放科学问题拆解成研究计划、候选假设、数据实验、证据审查、假设修正和下一步验证方案。

主研究问题：

> 当前第 25 太阳活动周的观测信号，能否为第 26 太阳活动周的强度趋势和物理机制提供证据？哪些太阳发电机机制假设最能被现有数据支持？

项目主线选择：

**以第 26 太阳活动周强度预测与机制解释为主任务，以 11 年周期机制证据挖掘和太阳活动指标关系漂移分析为辅助证据模块。**

这样设计的原因：

- “第 26 太阳活动周预测”有明确输入和输出，适合做 API、前端和测试案例。
- “11 年周期起源探秘”能体现太阳物理问题本身，而不是普通时序预测。
- “指标关系漂移分析”能展示 AI 的自我校正能力：当数据关系不稳定时，系统会降低置信度并生成修正实验。

## 2. 核心科学任务

### 2.1 主任务：第 26 太阳活动周强度预测与机制解释

系统需要回答：

- 第 26 太阳活动周可能偏强、偏中等还是偏弱？
- 预测结果主要依赖哪些观测指标？
- 极区磁场、太阳黑子数、F10.7 射电流量等指标是否支持某些前兆假设？
- 哪些证据反对当前预测？
- 下一步应补充哪些观测或实验来验证结论？

输出不追求给出绝对确定的科学结论，而是给出可检查的预测区间、证据链、置信度和验证方案。

### 2.2 辅助任务一：11 年周期起源机制证据挖掘

系统分析长期太阳活动数据，围绕以下机制生成和审查证据：

- Babcock-Leighton 太阳发电机机制。
- 极区磁场反转与下一周期强度的关系。
- 约 22 年 Hale 磁周期与 11 年太阳黑子周期之间的联系。
- 周期长度、上升时间、下降时间与活动周强度之间的关系。

该模块为主任务提供物理解释背景。

### 2.3 辅助任务二：太阳活动指标关系漂移分析

系统检查不同太阳活动周内，关键指标之间的关系是否稳定，例如：

- F10.7 与太阳黑子数之间的关系是否跨周期稳定。
- 上升期斜率与周期峰值之间的关系是否稳定。
- 前一周期强度、周期长度和下一周期强度之间的关系是否存在变化。

如果发现关系漂移，系统需要：

- 降低相关模型或假设的置信度。
- 生成新的非平稳性假设。
- 触发特征消融或分周期回测实验。

## 3. 产品目标

系统最终要让评委或用户看到一个完整的 AI 科研闭环：

1. 用户选择一个太阳活动周研究任务。
2. Pi Agent 生成研究计划。
3. 系统加载并清洗观测数据。
4. 系统构建周期级和时间序列特征。
5. 实验 Agent 自动运行多组模型和诊断实验。
6. 假设 Agent 生成候选物理假设。
7. 证据审查 Agent 对每条假设打分。
8. 系统根据反例、不确定性和实验失败记录修正假设或实验。
9. 用户查看前端结果，并通过 API 获取结构化输出。
10. 系统导出技术报告或研究摘要。
11. 知识管理子Agent把本轮findings、反例与失败实验经验以candidate身份写入LLM Wiki，经审核门后部分晋升为canonical，使下一次研究运行可在已有知识基础上继续推进。

对应竞赛提交材料：

- **可调用测试 API**：用于发起研究任务、查询实验结果、获取假设评分和导出报告。
- **可交互前端入口**：用于选择研究任务、查看数据、实验日志、假设卡片和证据链。
- **代表性测试案例**：覆盖第 26 周预测、极区前兆假设检验、F10.7 关系漂移分析和 11 年周期机制审查。
- **详细技术报告和源码**：说明数据管线、Agent 编排、模型实验、证据评分和自我校正机制。
- **可选演示视频**：10 分钟内展示一次完整的“假设生成-实验验证-证据审查-修正输出”流程。

## 4. 系统架构

## 4.1设计目标与总体定位

本部分说明Solar-Cycle Co-Scientist的系统架构和子Agent设计。系统面向2026年“挑战杯·揭榜挂帅”阿里云榜题XH-202619“基于国产开源大模型的AI Scientist研发与应用”，对应赛道一“科学问题”、方向二“金乌·太阳物理建模迭代与假设生成”中的B3“太阳活动周起源探秘”。官方要求作品围绕明确科学问题，展示数据预处理、特征构建、模型预测、结果评估、自我校正或证据推理，并提出下一步验证方案；因此，本系统的目标不是单点给出太阳黑子数预测，而是构建一个能够参与太阳物理研究过程的AI Scientist：它可以把开放科学问题拆解为研究计划，自动整理数据和特征，运行诊断实验，生成候选物理假设，审查证据和反例，并在证据不足或结论过强时主动修正。

本系统采用“两层Agent架构 + 横向知识基础设施”：

- 外层是一个统一科研主智能体，负责面向用户、评委和系统前端，接收任务、组织流程、维护上下文并输出最终结论。
- 内层是六个专业子Agent，其中五个负责研究规划、数据与特征、自动实验、科学假设生成、证据审查与修正的线性科研流程，第六个是知识管理子Agent，作为横向贯穿的“知识管家”，负责维护LLM Wiki知识库。
- 横向能力层由Qwen/阿里云百炼语言推理能力、数据处理与实验harness、文献证据检索、太阳物理知识约束、可视化与报告导出等skills/插件组成，为各子Agent提供可调用能力；其中LLM Wiki作为横向知识基础设施，被主智能体和全部科研流程子Agent共享消费，提供领域知识grounding、跨运行研究记忆与溯源链。

这种结构适合Pi Agent或类似智能体平台的编排方式：用户看到的是一个完整的科研助手，系统内部则通过多个专业角色协同完成复杂科研任务。五个科研流程子Agent的职责边界、协作逻辑和可信度控制共同决定系统是否能够形成可审查、可迭代的科研闭环；知识管理子Agent与LLM Wiki横向基础设施共同保证每次推理都能落到已有领域知识与历史研究经验之上，并使知识可积累、可溯源；横向skills/插件层则保证每一次推理都能落到数据、文献、实验、图表和报告等可检查产物上。

本架构有五个核心判断：

1. **太阳活动周问题必须由物理机制驱动。**  
   系统不能只输出预测曲线或模型分数，而要解释这些结果与太阳发电机机制、极区磁场前兆、活动周形态和代理指标漂移之间的关系。

2. **大模型主要承担科研组织和证据推理。**  
   大模型适合规划研究、总结证据、生成假设、审查表述和提出下一步实验；但不应替代真实数据计算，也不应擅自创造数值结果。

3. **闭环比单次结果更重要。**  
   评委看到的不应只是一次类似“第26太阳活动周强度判断”的回复，而应是一个可以反复迭代的科研流程：假设被提出，实验被执行，证据被审查，结论被修正，下一轮验证被规划。

4. **skills/插件必须服务于科学证据链。**  
   文献检索、数据处理、自动实验、模型批判、证据审查、图表绘制和报告导出不是彼此割裂的工具清单，而应统一进入研究状态记录，使评委能够追溯每个结论由哪些数据、实验、证据和修正动作支撑。

5. **知识必须可溯源、可积累。**  
   领域知识与历史研究经验必须沉淀在LLM Wiki中，供所有子Agent共享grounding；每条知识都带来源、置信度和适用范围，运行产出的新知识以candidate身份进入知识库，经审核门晋升后才成为canonical。这样系统每次运行都不归零，且任何结论都能追溯到所依据的知识条目。

### 4.1.1构建思路

本系统不是简单复用已有AI Scientist框架，而是参考官方赛题要求、Google Co-Scientist的假设演化机制和autoresearch的自动实验迭代思想，转化为面向B3太阳活动周问题的四类架构亮点：

- 形成“统一科研主智能体 + 六个子Agent（五个科研流程子Agent + 一个知识管理子Agent） + Qwen/百炼能力层 + LLM Wiki横向知识基础设施”的可验收架构：主智能体维护完整研究状态，科研流程子Agent分别完成规划、数据、实验、假设和审查，知识管理子Agent维护领域知识与跨运行研究记忆，数值结论由可复现实验链路支撑。

-   形成结构化假设演化机制：科学假设子Agent生成假设卡，证据审查子Agent执行评分、反证、排序和降权，统一主智能体根据审查结果决定是否进入下一轮修正。
- 形成自动实验迭代机制：自动实验子Agent记录每轮配置、数据版本、评价指标、失败原因和下一轮建议，使实验结果真实影响后续假设与研究计划。
- 形成跨运行知识积累机制：知识管理子Agent与LLM Wiki把领域canonical知识、历史研究发现、反例和失败经验沉淀为可检索、可溯源、可演化的知识库；运行产出的新知识以candidate身份进入，经审核门晋升，使系统每次运行都不归零，并让任何结论都可追溯到所依据的知识条目。

因此，本系统的架构不只是“使用多个Agent”，而是把太阳活动周起源探秘转化为可检查的AI Scientist状态机：每一次规划、实验、假设、审查、修正和知识沉淀都有输入、输出、证据边界和下一步动作。

系统一次典型运行可概括为：

```text
研究任务输入
  → 知识检索（各子Agent从LLM Wiki获取领域知识与历史研究经验grounding）
  → 研究规划
  → 数据加载与质量检查
  → 周期级和物理特征构建
  → 预测实验、回测实验与诊断实验
  → 候选太阳物理假设生成
  → 证据评分、反例检查与置信度修正
  → 结构化结论、下一步验证计划和报告输出
  → 候选知识写回（知识管理子Agent把本轮findings、反例、失败经验以candidate身份写入LLM Wiki）
```

## 4.3统一科研主智能体

### 4.3.1角色定位

统一科研主智能体是整个系统的“科研项目负责人”。它不直接替代所有子Agent工作，而是负责理解用户意图、组织研究流程、维护全局状态和汇总最终结论。

在本项目中，统一主智能体的关键价值在于把“第26太阳活动周强度趋势与机制解释”这类开放问题转化为一个可执行、可审查、可迭代的科研任务。它需要同时管理四类信息：

- 科学问题：当前研究的核心问题是什么，属于预测、机制解释还是证据审查。
- 数据与实验状态：已经使用了哪些观测数据，完成了哪些实验，哪些结果存在警告。
- 假设与证据状态：哪些机制假设被支持，哪些被削弱，哪些需要下一轮验证。
- 知识状态：本轮使用了LLM Wiki中的哪些canonical知识，产出了哪些候选知识，是否存在与已有知识的冲突。

### 4.3.2核心职责

统一科研主智能体负责：

1. **任务识别与范围控制**  
   判断用户任务是否属于B3范围。如果用户问题偏向纯数据拟合，主智能体需要把任务重新收束到“太阳活动周起源、演化和发电机机制解释”。

2. **子Agent调度**  
   决定调用研究规划、数据与特征、自动实验、科学假设和证据审查子Agent的顺序，并在必要时开启下一轮迭代。

3. **全局状态维护**  
   维护一次研究运行中的任务目标、数据版本、实验设置、候选假设、证据评分、置信度变化和修正记录。

4. **冲突协调**  
   当不同子Agent给出相互张力的结果时，主智能体需要协调。例如，预测模型显示某一趋势较强，但指标漂移分析提示关系不稳定，此时最终结论必须降低置信度。

5. **输出汇总与边界检查**  
   在最终输出前检查是否存在过度表述，避免把“趋势判断”写成“确定预报”，或把“相关关系”写成“机制证明”。

6. **知识冲突协调**  
   当本轮新发现与LLM Wiki中的canonical知识矛盾，或不同来源知识相互冲突时，主智能体负责协调裁决：决定是触发知识冲突审查、降级相关假设置信度，还是把矛盾作为新反例候选写回知识库，而不是任由冲突被静默忽略。

7. **签发候选知识写回**  
   在一次研究运行结束前，主智能体负责汇总本轮findings、反例与失败实验经验，签发给知识管理子Agent以candidate身份写入LLM Wiki，使研究经验得以跨运行积累，但不擅自晋升为canonical。

### 4.3.3输入与输出

**输入包括：**

- 用户选择或输入的研究任务。
- 数据源和分析范围设定。
- 最大迭代轮数和是否启用自我修正。
- 人工反馈或评审追加问题。

**输出包括：**

- 本轮研究任务定义。
- 子Agent调用轨迹。
- 预测或机制判断的结构化摘要。
- 候选假设排序。
- 支持证据、反对证据和不确定性说明。
- 下一步验证方案。
- 知识使用日志（本轮检索、引用与产出的LLM Wiki知识条目）和候选知识写回清单。

### 4.3.4主智能体的决策规则

统一主智能体必须遵循以下决策规则：

| 情形                       | 决策                                   |
| -------------------------- | -------------------------------------- |
| 用户要求直接预测第26周强度 | 转化为“趋势判断 + 机制证据 + 置信边界” |
| 数据覆盖不足               | 允许输出阶段性判断，但必须降低置信度   |
| 模型结果与物理约束冲突     | 优先保留物理边界，要求补充实验         |
| 子Agent输出缺少反证        | 要求假设生成或证据审查环节补充反例     |
| 人工反馈指出过度表述       | 触发表述修正和结论降级                 |
| 本轮新发现与canonical知识矛盾 | 触发知识冲突审查，降级相关假设，或把矛盾作为新反例候选写回LLM Wiki |
| 某假设依赖的知识条目被降级或废弃 | 重新评估该假设置信度，必要时进入下一轮修正 |

## 4.4研究规划子Agent

### 4.4.1角色定位

研究规划子Agent负责把开放科学问题拆解成可执行研究计划。它相当于科研项目中的“课题设计者”：先明确问题，再安排数据、实验、假设和评估方式。

在B3任务中，研究规划子Agent不能只安排“训练一个模型预测太阳黑子数”。它必须把主任务拆成若干与太阳物理机制相关的子问题，例如：

- 极区磁场前兆是否支持下一活动周强度判断？
- 活动周上升期斜率、周期长度和峰值之间是否存在稳定关系？
- F10.7与太阳黑子数之间的关系是否跨周期稳定？
- 南北半球不对称是否提示随机扰动或非轴对称发电机成分？
- 当前证据更支持哪类太阳发电机机制假设？

### 4.4.2核心职责

研究规划子Agent负责：

1. **任务转译**  
   将用户输入转化为系统可执行的科研任务。例如把“预测第26周强度”转译为“基于第25周后期观测信号，对第26周趋势进行有边界判断，并解释其发电机机制含义”。

2. **实验路线设计**  
   决定需要哪些实验模块：基线预测、周期回测、极区前兆检验、指标漂移分析、特征消融、机制假设审查等。

3. **假设方向预设**  
   给科学假设子Agent提供候选机制方向，例如Babcock-Leighton机制、极区场前兆、Waldmeier效应、代理指标漂移和非对称发电机扰动。

4. **评价标准设定**  
   明确每个任务如何评价：预测误差、回测稳定性、反例周期、特征敏感性、物理一致性和可检验性。

5. **停止与修正规则设定**  
   定义何时可以输出阶段性结论，何时必须进入下一轮修正。

### 4.4.3输入与输出

**输入包括：**

- 研究任务名称或自然语言问题。
- 用户选择的数据范围。
- 是否启用多轮迭代。
- 当前已有的证据摘要。

**输出包括：**

- 研究问题重述。
- 实验路线。
- 所需数据类型。
- 候选假设方向。
- 评价指标。
- 置信度降级触发条件。

### 4.4.4规划示例

当用户选择“第26太阳活动周预测与机制解释”时，研究规划子Agent可生成如下研究路线：

1. 整理长期太阳黑子数、F10.7和极区前兆相关数据。
2. 切分历史太阳活动周并构建周期级特征。
3. 运行基线预测和回测，得到趋势判断。
4. 检查极区前兆与下一周期峰值之间的关系。
5. 分析F10.7与太阳黑子数关系是否存在漂移。
6. 生成候选机制假设。
7. 由证据审查子Agent进行评分与降权。
8. 若出现高不确定性，进入下一轮修正。

### 4.4.5质量要求

研究规划子Agent输出的计划必须满足：

- 至少包含一个数据实验。
- 至少包含一个机制假设方向。
- 至少包含一个反证或不确定性检查。
- 至少包含一个下一步验证方案。
- 不允许把“预测结果”作为唯一目标。

### 4.4.6知识库使用方式

研究规划子Agent在生成研究路线时，应从LLM Wiki检索已知机制、标准实验范式与历史研究路线，避免重复造轮子或漏掉公认的关键实验（如Waldmeier效应检验、极区前兆回测、F10.7漂移分析）。检索到的canonical知识用于约束研究问题的物理边界，检索到的历史finding用于判断哪些子问题已有部分答案、哪些仍是开放问题。规划输出中应标注所依据的知识条目id，使研究路线可溯源。

## 4.5数据与特征子Agent

### 4.5.1角色定位

数据与特征子Agent负责把太阳活动观测资料转化为可供实验和假设推理使用的结构化特征。它相当于系统中的“观测资料专家”和“物理特征工程师”。

在B3的AI for Science任务中，特征层必须有明确太阳物理含义。系统不仅要知道某个变量是否有预测效果，还要说明它可能对应太阳活动周中的哪一类物理过程。

### 4.5.2候选数据类型

数据与特征子Agent重点考虑以下类型数据：

| 数据类型                | 作用                                         |
| ----------------------- | -------------------------------------------- |
| 太阳黑子数长期序列      | 描述太阳活动周强度、周期长度和峰值演化       |
| F10.7射电流量           | 作为太阳活动水平的代理指标，用于检查指标关系 |
| 极区磁场或极区前兆proxy | 用于检验下一周期强度前兆假设                 |
| 活动周起止与峰值元数据  | 用于构建周期级特征和回测样本                 |
| 南北半球活动指标        | 用于分析半球不对称和非轴对称扰动             |

### 4.5.3核心职责

数据与特征子Agent负责：

1. **数据加载与清洗**  
   对不同来源的观测数据进行时间对齐、缺失处理和异常标记。

2. **周期切分**  
   根据活动低谷、峰值和长期趋势，将观测序列组织成活动周级样本。

3. **周期级特征构建**  
   提取峰值强度、谷值、周期长度、上升期时长、下降期时长、上升斜率、积分活动量等特征。

4. **物理代理特征构建**  
   构建极区前兆、F10.7关系特征、南北半球不对称和跨周期漂移指标。

5. **数据质量说明**  
   标记哪些数据适合主证据链，哪些只能作为辅助参考，哪些暂时不能支撑强结论。

### 4.5.4输入与输出

**输入包括：**

- 研究规划中列出的数据需求。
- 可用观测数据及其说明。
- 用户额外上传的参考材料或数据样例。

**输出包括：**

- 清洗后的时间序列。
- 活动周切分结果。
- 周期级特征表。
- 数据质量说明。
- 代理指标解释。
- 缺失数据和替代proxy标记。

### 4.5.5特征与物理含义映射

| 特征              | 可能物理含义                           |
| ----------------- | -------------------------------------- |
| 周期峰值强度      | 活动周整体强度，可对应环向磁场活动表现 |
| 上升期时长        | 与活动周增长速度和Waldmeier效应相关    |
| 周期长度          | 可能反映发电机过程时间尺度变化         |
| 极区前兆强度      | 对下一周期种子极向场的约束             |
| F10.7与黑子数关系 | 活动代理指标之间的稳定性或漂移         |
| 南北半球不对称    | 随机涌现、跨赤道耦合或非轴对称成分     |

### 4.5.6质量要求

数据与特征子Agent必须遵守：

- 不把短时耀斑数据替代长期活动周主数据。
- 不把F10.7或黑子数直接称为太阳内部磁场。
- 不隐藏数据缺失或覆盖不足。
- 不在缺少极区前兆数据时给出高置信度机制判断。
- 每个重要特征都要有物理解释或明确标记为经验代理。

### 4.5.7知识库使用方式

数据与特征子Agent在加载与清洗数据时，应从LLM Wiki检索相应数据源说明条目（data_source类），获取数据采集方法、已知偏差、版本校正历史与适用范围（例如SILSO太阳黑子数的版本演化、F10.7的调整历史、Polar Field Proxy的有效区间）。在构建特征时，应检索概念与机制条目（concept、mechanism类）确认特征的物理含义标注是否与canonical知识一致，避免对特征做出超出物理共识的解释。数据质量说明中应引用所依据的数据源知识条目。

## 4.6自动实验子Agent

### 4.6.1角色定位

自动实验子Agent负责运行预测实验、回测实验和诊断实验。它是系统从“假设想法”走向“证据检验”的关键环节。

在本项目中，自动实验不只服务于预测误差优化，还服务于科学解释。一个模型即使预测误差较低，如果完全依赖不稳定代理指标，也不能被视为强机制证据；相反，一个简单实验即使不能给出精确预测，只要能揭示极区前兆、Waldmeier效应或指标漂移，就具有科学价值。

### 4.6.2实验类型

自动实验子Agent包含以下实验类别：

| 实验类别           | 目的                                  |
| ------------------ | ------------------------------------- |
| 统计基线实验       | 提供最简单可解释的参照结果            |
| 周期相似性实验     | 检查历史相似周期对当前趋势的提示      |
| 回归与轻量预测实验 | 得到趋势判断和关键特征贡献            |
| 特征消融实验       | 检查模型是否过度依赖单一指标          |
| 分周期回测实验     | 检查结论在历史周期上的稳定性          |
| 极区前兆实验       | 检验极区磁场或proxy与下一周期强度关系 |
| 指标漂移实验       | 检查F10.7与黑子数关系是否跨周期变化   |
| 机制诊断实验       | 将统计结果转化为发电机机制线索        |

### 4.6.3核心职责

自动实验子Agent负责：

1. **执行研究规划中的实验路线。**
2. **比较不同模型和特征组合。**
3. **记录实验设置、结果、失败原因和警告信息。**
4. **识别不稳定结果，例如对单一特征过度敏感。**
5. **把实验结果转化为假设生成子Agent可理解的证据摘要。**

### 4.6.4输入与输出

**输入包括：**

- 周期级特征。
- 时间序列特征。
- 研究规划中的实验任务。
- 评价指标和停止条件。

**输出包括：**

- 实验结果摘要。
- 模型对比结果。
- 关键特征解释。
- 回测误差或稳定性评价。
- 失败实验记录。
- 下一轮实验建议。

### 4.6.5实验结果分级

自动实验子Agent不应只输出“成功/失败”，而应进行科学分级：

| 等级   | 含义                                               |
| ------ | -------------------------------------------------- |
| 通过   | 实验结果稳定，且与物理解释基本一致                 |
| 警告   | 结果有一定价值，但存在样本少、漂移、敏感性高等问题 |
| 失败   | 实验无法支撑假设，或结果与关键约束冲突             |
| 待补充 | 需要新增数据或人工判断后才能继续                   |

### 4.6.6质量要求

自动实验子Agent必须保证：

- 每个重要结论至少有一个实验依据。
- 每个实验结果都说明适用范围和限制。
- 出现实验失败时不掩盖，而是进入自我修正流程。
- 预测结果不能脱离回测、消融和物理解释单独出现。

### 4.6.7知识库使用方式

自动实验子Agent在执行实验前，应从LLM Wiki检索标准实验范式条目（experiment_paradigm类），保证回测、特征消融、漂移检测等实验的设计与公认做法一致。在得到实验结果后，应检索历史finding条目进行对比，判断本次结果是否复现已知结论，或是否与已有反例条目（counterexample类）相冲突。若出现与canonical知识显著偏离的结果，不应直接采信或直接否定，而应标记为待审查并交给证据审查子Agent与主智能体。实验结果摘要中应记录所对比的知识条目。

## 4.7科学假设子Agent

### 4.7.1角色定位

科学假设子Agent负责根据研究问题、物理背景和实验结果生成候选科学假设。它是系统体现“AI Scientist”能力的核心模块之一。

该子Agent生成的不是自由文本摘要，而是结构化假设卡。每张假设卡都应说明：假设是什么，为什么可能成立，当前有哪些支持证据，可能被什么反例削弱，下一步如何验证。

### 4.7.2核心职责

科学假设子Agent负责：

1. **生成候选物理机制假设。**
2. **把实验结果解释为太阳发电机机制线索。**
3. **为每条假设绑定可观测证据。**
4. **提出可检验预测。**
5. **列出可能混杂因素和反证条件。**

### 4.7.3输入与输出

**输入包括：**

- 研究规划中的候选假设方向。
- 自动实验子Agent输出的结果。
- 数据与特征子Agent提供的物理特征说明。
- 证据材料和太阳物理背景知识。

**输出包括：**

- 候选假设列表。
- 每条假设的物理机制。
- 支持证据。
- 反对证据或限制。
- 可检验预测。
- 下一步验证方案。

### 4.7.4假设卡结构

每张假设卡建议包含：

| 字段       | 说明                               |
| ---------- | ---------------------------------- |
| 假设名称   | 用一句话概括机制判断               |
| 物理动机   | 说明与太阳发电机或活动周演化的关系 |
| 观测证据   | 当前数据支持该假设的部分           |
| 实验证据   | 自动实验中与该假设相关的结果       |
| 反证条件   | 哪些结果会削弱或推翻该假设         |
| 不确定性   | 数据、模型或物理解释上的限制       |
| 下一步验证 | 后续应补充的数据或实验             |

### 4.7.5候选假设示例1. **极区前兆假设**  
   如果第25周后期或极小期附近的极区前兆信号偏弱，则第26周峰值可能弱于或不强于第25周。该假设需要极区磁场长期数据支持，且必须承认样本周期有限。

2. **Waldmeier约束假设**  
   活动周峰值与上升期速度之间的关系可能反映太阳发电机系统中的非线性放大或饱和过程。该假设需要通过历史周期形态回测来检验。

3. **代理指标漂移假设**  
   F10.7与太阳黑子数的关系可能随周期阶段或活动强度变化而漂移。因此，单独依赖某一代理指标的预测模型应降低置信度。

4. **周期长度状态假设**  
   异常周期长度可能反映太阳内部发电机状态变化，并影响下一周期强度。但该假设容易受样本量和历史周期差异影响。

5. **半球不对称扰动假设**  
   南北半球活动不同步可能提示随机磁通涌现、跨赤道耦合或非轴对称发电机成分，需要引入半球数据进行验证。

### 4.7.6质量要求

科学假设子Agent必须避免：

- 只生成“看起来合理”的解释，却没有可检验预测。
- 只列支持证据，不列反证条件。
- 把相关性写成因果机制。
- 把当前趋势判断写成确定性预报。
- 忽略数据覆盖不足和代理指标局限。

### 4.7.7知识库使用方式

科学假设子Agent在生成候选假设时，必须以LLM Wiki中的机制与概念条目（mechanism、concept类）作为物理grounding，确保每条假设的物理动机符合canonical知识，而不是由大模型凭空编造物理关系。同时应检索反例条目（counterexample类）与假设模板条目（hypothesis_template类），把已知反证条件直接绑定到假设卡上，并复用可检验预测的结构。每张假设卡应标注所引用的知识条目id，使假设的可溯源、可审查。

## 4.8证据审查子Agent

### 4.8.1角色定位

证据审查子Agent负责对候选假设进行科学批判、证据评分和置信度修正。它是系统避免“只会生成、不会审查”的关键模块。

该子Agent借鉴Co-Scientist中生成、批判、排序和演化的思想：假设生成之后必须接受审查，审查之后必须能触发修正。这样系统不只停留在灵感式假设生成，而能形成有证据、有反证、有迭代记录的科研协作流程。

### 4.8.2核心职责

证据审查子Agent负责：

1. **检查证据完整性**  
   每条假设是否有数据支持、实验支持、物理解释和反证条件。

2. **评估物理合理性**  
   假设是否符合太阳活动周和太阳发电机理论的基本框架。

3. **识别反例和限制**  
   哪些历史周期、指标漂移或数据缺失会削弱该假设。

4. **进行假设排序**  
   按照数据支持度、物理一致性、可检验性和不确定性对假设排序。

5. **触发自我修正**  
   如果证据不足、模型不稳定或结论过强，则要求系统降低置信度或进入下一轮实验。

### 4.8.3输入与输出

**输入包括：**

- 科学假设子Agent生成的假设卡。
- 自动实验子Agent输出的实验结果。
- 数据与特征子Agent输出的数据质量说明。
- 研究规划子Agent设定的评价标准。

**输出包括：**

- 假设排名。
- 证据评分。
- 支持证据摘要。
- 反对证据摘要。
- 置信等级。
- 降权原因。
- 下一步验证方案。

### 4.8.4证据评分维度

采用多维评分：

| 维度       | 含义                                       |
| ---------- | ------------------------------------------ |
| 数据支持度 | 当前观测数据是否直接支持该假设             |
| 模型一致性 | 预测实验或诊断实验是否与假设一致           |
| 物理合理性 | 是否符合太阳发电机理论和活动周物理图像     |
| 反例压力   | 是否存在明显反例周期或矛盾证据             |
| 不确定性   | 数据覆盖、样本量、代理指标和模型稳定性限制 |
| 可检验性   | 下一步能否设计清晰实验继续验证             |
| 表述风险   | 是否容易被误读为确定性预报或因果证明       |

### 4.8.5置信度修正规则

证据审查子Agent应在以下情况下触发降权：

| 触发条件                        | 修正方式                           |
| ------------------------------- | ---------------------------------- |
| 极区前兆数据覆盖周期太少        | 降低预测置信度，保留机制约束       |
| 模型高度依赖F10.7等单一代理指标 | 要求特征消融，并降低单模型结论权重 |
| 历史回测不稳定                  | 降低预测强度，转为趋势性表述       |
| 假设缺少反证条件                | 要求假设生成子Agent补充反证        |
| 表述接近“官方预报”              | 改写为“机制证据支持的趋势判断”     |

### 4.8.6输出示例

对于“极区前兆假设”，证据审查子Agent可能给出：

- 支持证据：极区磁场前兆在若干历史周期中与下一周期强度存在对应关系。
- 反对证据：可用极区磁场记录覆盖周期有限，无法支撑确定性第26周预报。
- 置信等级：中等偏高，但仅限机制约束。
- 下一步验证：补充更长时间跨度的极区代理数据，比较不同前兆方法在历史周期中的回测表现。

### 4.8.7知识库使用方式

证据审查子Agent是LLM Wiki最重度的外部消费者。它使用canonical机制与概念条目判断假设的物理合理性，使用反例条目库检索是否存在削弱该假设的历史周期或矛盾证据，使用数据源说明条目核查证据所依赖数据的覆盖与偏差。审查过程中还应检查表述风险：若假设表述与canonical知识中的边界（如“相关非因果”“小样本”）冲突，应触发表述修正。审查输出中的证据评分与降权理由应引用所依据的知识条目，形成可复查的证据—知识对照。

## 4.9知识管理子系统（LLM Wiki）

### 4.9.1角色定位

知识管理子系统是系统的「长期科研记忆与领域知识底座」。前五个科研流程子Agent（规划、数据、实验、假设、审查）面向单次研究运行，负责把开放科学问题推进到结构化结论；而知识管理子系统跨越单次运行，负责把领域 canonical 知识和历史研究经验沉淀下来，使系统在每次运行时不归零。

本子系统采用「横向知识库 + 专职知识管理子Agent」的混合结构：

- **横向知识基础设施（LLM Wiki）**：持久化存储、检索、溯源能力的共享资源，被主智能体和全部科研流程子Agent共同消费。它不是任何一个子Agent的私有产物，而是全系统 grounding 与可溯源的事实来源。
- **知识管理子Agent（第6个子Agent）**：作为「知识管家」，负责文献与数据摄取、检索响应、从研究运行产出候选知识、执行晋升与废弃生命周期、维护溯源日志。它不参与规划→数据→实验→假设→审查的线性科研流程，而是横向贯穿于整个系统。

之所以采用混合结构而非把知识管理完全塞进某一个线性子Agent，是因为知识具有横向属性：研究规划需要历史路线，数据子Agent需要数据源说明，实验子Agent需要实验范式，假设子Agent需要机制 grounding，审查子Agent需要 canonical 判据与反例库。若把知识管理塞进其中任一子Agent，其他子Agent都将失去稳定的知识入口。因此，知识库作为横向基础设施被共享，同时由专职知识管理子Agent统一维护，保证知识的一致性、可审查性和可积累性。

### 4.9.2三大职能

知识管理子系统承担三类相互独立但彼此支撑的职能：

1. **领域知识库（Domain Knowledge Base）**  
   把太阳物理的 canonical 事实固化下来，供大模型 grounding，避免大模型在生成假设、解释机制或表述结论时擅自创造数值结果或编造物理关系。领域知识库包括核心概念（太阳活动周、F10.7、极区场、Waldmeier效应、Hale磁周期等）、主流机制（Babcock-Leighton发电机、极区场反转、差分旋转等，含支持证据、反证与当前争议）、数据源说明（采集方法、已知偏差、校正历史、适用范围）、标准实验范式与假设模板。

2. **研究记忆（Research Memory）**  
   让每次研究运行不归零，沉淀跨运行积累的经验。研究记忆包括历史运行记录、已验证或已否决的假设库、积累的反例库（如「cycle X 在该指标上违反 Waldmeier 效应」）、实验经验库（哪些配置成功、哪些失败及原因）。研究记忆直接支撑系统「闭环比单次结果更重要」的原则：一次运行发现的反例或失败实验，可以成为下一次运行的初始约束。

3. **检索与溯源层（Retrieval & Provenance）**  
   所有子Agent在推理过程中可以检索知识库；每条知识都带来源（文献DOI、历史run_id、专家、教科书页码）、置信度、有效范围和引用链。任何子Agent的输出都能追溯到使用了哪些知识条目，使评委能够复现每一条结论的知识依据。溯源层是系统可审查性的底层保障。

### 4.9.3知识库构成与条目分类

知识库条目按内容性质分为两大类、七个子类型：

**领域知识库类：**

| 条目类型 type | 说明 | 在太阳活动周项目中的典型条目 |
| --- | --- | --- |
| concept | 核心概念定义与物理解释 | 太阳活动周、F10.7射电流量、极区磁场、Waldmeier效应 |
| mechanism | 物理机制及其证据状态 | Babcock-Leighton发电机、Hale 22年磁周期、极区场反转前兆 |
| data_source | 数据源说明、偏差与校正 | SILSO太阳黑子数版本演化、F10.7调整历史、Polar Field Proxy适用范围 |
| experiment_paradigm | 标准实验范式与评价指标 | 周期回测范式、特征消融范式、漂移检测范式 |
| hypothesis_template | 可复用的假设结构 | 「前兆强度→下一周期峰值」型假设模板 |

**研究记忆类：**

| 条目类型 type | 说明 | 典型条目 |
| --- | --- | --- |
| finding | 历史研究运行的发现 | 「SC21–SC25回测中极区前兆与下一周期峰值相关系数约0.7」 |
| counterexample | 积累的反例 | 「cycle X 在去除F10.7后预测失效，提示代理指标依赖」 |

### 4.9.4知识条目 Schema

每条知识条目统一采用如下结构化 schema：

| 字段 | 说明 |
| --- | --- |
| id | 唯一标识，格式 `kb_<type>_<slug>_<seq>` |
| type | concept / mechanism / data_source / experiment_paradigm / hypothesis_template / finding / counterexample |
| title | 一句话标题 |
| content | 结构化正文（定义、机制、支持证据、反证、当前现状、可检验预测等，按 type 不同选用子字段） |
| source_type | literature / textbook / dataset_doc / historical_run / expert / derived |
| source_ref | DOI / URL / run_id / 审核人 / 书页 |
| confidence | high / medium / low（或 0–1 数值） |
| status | canonical / candidate / deprecated / superseded |
| valid_range | 适用范围，如「SC21–SC25」「F10.7>70」「下降期」 |
| related_ids | 关联条目 id 列表 |
| provenance | 来源链：若由 candidate 晋升而来，记录支持它的 run_id 列表与晋升理由 |
| version | 版本号与变更历史 |
| created / updated / by | 创建时间、最后更新时间、责任 Agent 或人 |

### 4.9.5知识管理子Agent核心职责

知识管理子Agent作为知识管家，负责：

1. **摄取（Ingest）**  
   把外部文献、教科书、数据集文档、专家输入转化为 candidate 条目；在每次研究运行结束后，从统一主智能体汇总的 findings、反例、失败实验中提炼候选知识并写入知识库。

2. **检索响应**  
   响应其他子Agent的知识查询请求，按 type、关键词、有效范围、置信度等条件检索，返回条目及其溯源信息。

3. **候选写回**  
   在研究运行中，对发现的非平凡结论、反例或失败经验，写成 status=candidate 的条目；不允许直接晋升为 canonical。

4. **晋升与废弃生命周期管理**  
   维护 candidate → canonical 的审核门，以及 deprecated / superseded 的标记与替换；任何生命周期变更都记录理由与审核依据。

5. **冲突检测**  
   当新发现与已有 canonical 条目矛盾，或不同来源知识相互冲突时，主动触发冲突审查，由主智能体协调裁决，而非静默覆盖。

6. **溯源日志维护**  
   记录每次研究运行使用了哪些知识条目、产出哪些候选条目、晋升或废弃了哪些条目，形成可复现的知识演化轨迹。

### 4.9.6三大生命周期流程

知识条目从产生到退出，经历三个核心流程：

1. **摄取 Ingest**  
   来源包括：外部文献与教科书（由知识管理子Agent或人工导入）、数据集文档、专家输入、历史研究运行结束后的 findings 与反例、失败实验经验。所有摄取产物初始状态均为 candidate，且必须带 source_type 与 source_ref。

2. **晋升 Promote（审核门）**  
   candidate 晋升为 canonical 必须满足以下任一条件：
   - **跨运行复现**：同一条发现在至少 2 次独立研究运行中被复现，且无反例；
   - **文献支撑**：有同行评议文献或权威教科书直接支持；
   - **专家审核**：由领域专家人工审核通过。

   晋升时必须记录晋升理由、支持 run_id 或文献引用、审核人，并写入 provenance 字段。

3. **废弃/修正 Deprecate**  
   当出现以下情况时，旧条目进入 deprecated 或 superseded 状态：
   - 新观测数据或新研究结论与旧 canonical 条目矛盾；
   - 数据源发生版本校正，导致旧条目适用范围失效；
   - 机制理论被新证据显著削弱。

   废弃时不删除旧条目，而是标记状态、注明废弃原因与替代条目 id，保留版本历史，使知识演化可追溯、可回滚。

### 4.9.7与其他角色的交互

| 角色 | 如何使用 LLM Wiki |
| --- | --- |
| 研究规划子Agent | 检索已知机制、实验范式与历史研究路线，避免重复造轮子或漏掉标准实验 |
| 数据与特征子Agent | 检索数据源说明、特征物理含义、已知偏差与校正历史 |
| 自动实验子Agent | 检索实验范式、与历史发现对比、判断本次结果是否复现已知结论 |
| 科学假设子Agent | 用机制知识 grounding 假设、与已知反例比对、引用可检验预测模板 |
| 证据审查子Agent | 用 canonical 知识判断物理合理性、检索积累的反例库、检查表述风险 |
| 统一科研主智能体 | 协调知识冲突、签发候选知识写回、维护跨运行研究记忆 |
| 知识管理子Agent | 摄取 / 检索响应 / 候选写回 / 晋升废弃 / 冲突检测 / 溯源日志维护 |

### 4.9.8输入与输出

**输入包括：**

- 其他子Agent的检索请求（关键词、type、有效范围、置信度阈值）。
- 研究运行结束后的 findings、反例、失败实验摘要。
- 外部文献、教科书、数据集文档与专家输入。
- 主智能体的晋升审核指令或废弃指令。

**输出包括：**

- 检索结果（条目列表及其溯源信息）。
- 新写入的 candidate 条目及其 id。
- 生命周期变更记录（晋升、废弃、替换）。
- 一次研究运行的知识使用日志与知识演化轨迹。

### 4.9.9质量要求

知识管理子Agent必须遵守：

- 不擅自把研究运行产出直接晋升为 canonical，必须经过审核门。
- 矛盾知识不静默覆盖，必须记录冲突并触发审查。
- 所有 canonical 条目必须有可追溯来源；无来源的条目只能停留在 candidate。
- 过时或被否决的条目不删除，必须保留并注明废弃原因与替代关系。
- 每条结论都应能追溯到所使用的知识条目，形成可复现的知识依据链。
- 领域知识库中的数值与物理关系必须来自权威来源，禁止由大模型自行编造。

## 4.10自我校正机制

自我校正不是独立子Agent，而是贯穿统一主智能体、自动实验子Agent和证据审查子Agent的横向能力。它用于识别数据不足、模型不稳定、证据链断裂和结论表述过强等问题，是系统从单次输出走向科研闭环的关键机制。

### 4.10.1自我校正触发条件

系统在以下情况下进入自我校正：

- 数据覆盖不足。
- 实验结果波动较大。
- 特征消融显示模型依赖不稳定指标。
- 候选假设缺少反证条件。
- 假设排序与物理常识冲突。
- 输出文本存在过度预测或过度证明风险。
- 人工反馈指出概念混淆。
- 本轮新发现与LLM Wiki中的canonical知识矛盾。
- 某条假设依赖的canonical知识条目被降级或废弃。

### 4.10.2自我校正动作

系统可以采取以下修正动作：

1. 降低结论置信度。
2. 将“预测”改写为“趋势判断”。
3. 要求自动实验子Agent增加消融实验或回测。
4. 要求数据与特征子Agent补充数据质量说明。
5. 要求科学假设子Agent补充反证条件。
6. 重新排序假设。
7. 将不成熟假设标记为“待验证”。
8. 触发知识冲突审查，由主智能体协调裁决新发现与canonical知识的矛盾。
9. 重新评估依赖被降级或废弃知识条目的假设，必要时调整其置信度或进入下一轮修正。

### 4.10.3自我校正示例

如果某个预测模型在包含F10.7时表现较好，但去除F10.7后性能明显下降，同时指标漂移实验显示F10.7与黑子数关系跨周期不稳定，则系统不能直接给出高置信度预测。它应触发以下修正：

- 将模型结论降级为“依赖代理指标的趋势提示”。
- 要求补充不含F10.7的对照实验。
- 在假设卡中加入“代理指标漂移风险”。
- 在最终报告中说明该结果不能单独作为机制证明。

## 4.11子Agent协作流程

### 4.11.1一次完整研究运行

以“第26太阳活动周趋势判断与机制解释”为例，一次完整运行如下：

1. 用户选择研究任务。
2. 统一科研主智能体确认任务属于B3范围。
3. 研究规划子Agent生成研究路线。
4. 数据与特征子Agent整理长期太阳活动数据并构建特征。
5. 自动实验子Agent运行预测、回测、特征消融和诊断实验。
6. 科学假设子Agent生成候选机制假设。
7. 证据审查子Agent对假设进行评分、排序和降权。
8. 统一科研主智能体检查是否需要自我修正。
9. 如果需要，系统返回规划或实验环节进行下一轮迭代。
10. 如果达到阶段性停止条件，系统输出结构化结论和报告摘要。

其中，第3至7步在执行过程中，各子Agent持续从LLM Wiki检索领域知识与历史研究经验进行grounding（知识检索），并在输出中标注所引用的知识条目；第10步结束后，知识管理子Agent把本轮findings、反例与失败实验经验以candidate身份写入LLM Wiki（候选写回），由主智能体签发，经审核门后才可能晋升为canonical。

### 4.11.3信息传递原则

子Agent之间的信息传递应遵循四条原则：

1. **结构化传递**  
   每个子Agent输出应尽量结构化，便于下一环节审查和复用。

2. **证据不丢失**  
   支持证据、反对证据、数据限制和失败实验都应保留，不能只传递最有利结果。

3. **边界随结论传递**  
   如果某个结论带有“小样本”“代理指标”“相关非因果”等限制，这些限制必须一直传递到最终报告。

4. **知识使用日志随结论传递**  
   每个子Agent在输出结论时，应同时传递所引用的LLM Wiki知识条目id，使最终报告中的每条结论都能追溯到所依据的canonical知识与历史研究经验。

## 4.13架构亮点

本架构的主要亮点不在于泛泛展示“多Agent”，而在于把AI Scientist方法落实到太阳活动周起源这一具体科学问题中：

1. **赛题定位高度贴合。**  
   系统直接面向XH-202619赛道一方向二B3，不把题目泛化成任意时间序列任务，而是以“第26太阳活动周趋势判断与机制解释”为可测试主线，以“11年周期起源机制”和“太阳活动指标关系漂移”为辅助证据模块。

2. **保留清晰的主Agent + 六子Agent + 横向知识基础设施框架。**  
   统一科研主智能体负责面向评委的单一入口，六个子Agent中五个承担规划、数据、实验、假设和审查的线性科研流程，知识管理子Agent横向贯穿维护LLM Wiki。架构足够清楚，便于Pi Agent或类似平台编排，也便于在前端和API中展示完整运行链条。

3. **Qwen/百炼与可复现实验链路分工明确。**  
   国产开源大模型能力主要用于问题理解、证据综合、假设生成、批判审查和报告表达；数值计算、模型评分、回测、消融和漂移诊断由可复现实验链路完成，避免把大模型生成内容误当作数据结论。

4. **skills/插件层进入统一研究状态。**  
   文献证据检索、太阳物理知识约束、数据处理、自动实验harness、可视化图件和报告导出等能力不是孤立工具，而是被统一主智能体调度，并在研究状态中留下输入、输出、证据来源和修正记录。

5. **吸收Co-Scientist的假设演化机制。**  
   假设子Agent不只生成候选机制，还要把每条假设写成可审查假设卡；证据审查子Agent进一步执行支持证据、反对证据、可检验预测、置信度和下一步验证方案的排序与修正。

6. **吸收autoresearch的实验迭代机制。**  
   自动实验子Agent记录每轮实验配置、指标、失败原因、保留/丢弃判断和下一轮建议，使实验结果真实影响后续研究计划，而不是只在最终报告中展示最有利结果。

7. **太阳物理反证机制更具体。**  
   系统把极区磁场前兆、Waldmeier约束、F10.7与黑子数关系漂移、活动周长度异常和南北半球不对称作为候选证据与反证入口，使假设审查具有太阳物理语义，而不是只做抽象文本评判。

8. **评审可验收性强。**  
   每轮运行都能输出研究计划、实验日志、假设卡、证据评分、自我校正记录和下一步验证方案；这些产物可以同时服务于技术报告、可交互前端、可调用API和10分钟演示视频。

9. **LLM Wiki形成跨运行研究记忆。**  
   领域canonical知识、历史研究发现、反例与失败实验经验沉淀在LLM Wiki中，被所有子Agent共享消费；系统每次运行都不归零，可在已有研究记忆基础上继续推进，而不是反复从零开始。

10. **读写分离 + 审核门保证知识可信度。**  
    运行只能向LLM Wiki写入candidate条目，晋升canonical必须满足“跨运行复现、文献支撑、专家审核”之一；矛盾知识不静默覆盖，而是标记deprecated/superseded并保留历史。这使系统能够积累经验，又不会把大模型幻觉或单次偶发结果固化成“事实”。

11. **全链路溯源使结论可复查。**  
    每条知识带来源、置信度与适用范围，每条结论带所引用的知识条目id；评委可以从最终报告的任意一条结论，反向追溯到支撑它的数据、实验、canonical知识与历史研究经验，形成完整的证据—知识对照链。

## 5. 核心用户流程

核心用户流程围绕科研 Dashboard 展开。用户不需要在多个页面之间跳转，而是按照研究流程向下滚动，逐步完成数据输入、周期分析、机制推理、假设审查和报告生成。

1. 用户进入 Solar-Cycle Co-Scientist 科研 Dashboard。
2. 用户选择内置数据源，或上传 CSV、太阳图像和文字材料等外部数据源。
3. 系统解析输入数据，并在当前页面展示识别字段、时间范围、缺失值和数据质量检查结果。
4. 用户确认数据配置并启动研究任务，系统创建一次研究运行。
5. Qwen 主 Agent 生成研究计划，并依次调度数据处理、周期分析、机制推理、自动实验、假设生成和证据审查 Agent。
6. 页面持续展示约 11 年太阳活动周期的演化规律、太阳发电机物理机制、模型对比和 Agent 实验日志。
7. 系统生成候选科学假设，并展示支持证据、反向证据、证据评分、置信度和不确定性说明。
8. 用户可以质疑当前结论；Qwen Agent 根据反馈补充反例、调整置信度、修订假设并生成新的验证方案。
9. 用户可在知识库区域检索LLM Wiki中的领域知识与历史研究经验，查看本轮引用的知识条目及其溯源，并浏览候选知识待审核队列与知识演化时间线。
10. 页面在最后展示完整研究报告预览，包括数据来源、周期规律、机制分析、候选假设、证据链、反馈修订记录和下一步验证计划。用户可选择以PDF等形式导出研究报告。

## 6. API 设计

API 的职责是调用 Unified Research Agent。外部调用者不需要知道内部有多少子 Agent，只需要提交研究任务并查询运行结果。子 Agent 的中间产物通过统一的 `run_id` 关联，并在实验、假设和报告接口中展示。

最小可提交 API：

```http
POST /api/research/run
GET  /api/research/{run_id}
GET  /api/research/{run_id}/experiments
GET  /api/research/{run_id}/hypotheses
GET  /api/research/{run_id}/knowledge
GET  /api/research/{run_id}/report
```

`POST /api/research/run` 示例输入：

```json
{
  "task": "cycle26_prediction",
  "data_sources": ["silso_sunspot", "f107", "polar_proxy"],
  "agent_mode": "hypothesis_experiment_review",
  "max_iterations": 3
}
```

示例输出：

```json
{
  "run_id": "cycle26_001",
  "prediction": {
    "target": "solar_cycle_26_peak_strength",
    "range": "medium-to-weak",
    "confidence": 0.64
  },
  "top_hypothesis": "Weak polar precursor signals imply a lower Solar Cycle 26 peak than Solar Cycle 25.",
  "evidence_score": 0.71,
  "next_validation": [
    "add updated polar field observations",
    "compare precursor model against cycles 21-25",
    "run feature ablation without F10.7"
  ]
}
```

可选扩展 API：

```http
GET  /api/datasets
GET  /api/features/{dataset_id}
POST /api/hypotheses/review
POST /api/report/export
```

知识管理 API（LLM Wiki）：

```http
GET  /api/knowledge/search?q=&type=&status=        # 检索知识条目
GET  /api/knowledge/{id}                            # 获取单条知识详情
GET  /api/knowledge/{id}/provenance                 # 获取条目溯源链（来源、晋升run_id、审核人）
POST /api/knowledge/propose                         # 从研究运行写回 candidate（由知识管理子Agent调用）
POST /api/knowledge/{id}/promote                    # candidate 晋升 canonical（走审核门）
POST /api/knowledge/{id}/deprecate                  # 标记条目废弃/被替代（保留历史）
```

`GET /api/knowledge/search` 示例输出：

```json
{
  "query": "polar field precursor",
  "results": [
    {
      "id": "kb_mechanism_polar_precursor_001",
      "type": "mechanism",
      "title": "Polar field precursor and next-cycle amplitude",
      "confidence": "medium",
      "status": "canonical",
      "valid_range": "SC21–SC25",
      "source_ref": "doi:10.1029/...",
      "related_ids": ["kb_counterexample_cycle_x_003"]
    }
  ]
}
```

## 7. 前端设计

前端所有研究功能集中在一个单页科研 Dashboard 中，并按照真实科研流程纵向排列。用户通过滚动浏览完整研究过程，也可以点击左侧导航，通过锚点平滑滚动到对应 Section；滚动过程中，导航会自动高亮当前区域。

桌面端采用三栏布局：左侧为固定研究导航，中间为主要研究内容，右侧为 sticky 的 Qwen Agent 运行摘要，用户可点击具体流程查看 Agent 运行详情。顶部 Header 固定显示项目名称、Run ID、任务状态和报告导出入口。小屏设备下，三栏布局自动转换为单栏，所有 Section 按研究顺序依次展示。

### 7.0 前端整体交互流程

- 用户进入 Dashboard 后，从左侧导航或页面顶部开始研究流程。
- 用户选择内置太阳观测数据，或上传 CSV、PNG、JPG、TXT 等外部材料。
- 系统对上传内容进行字段识别、格式校验和数据质量检查，并在当前 Section 内反馈解析状态。
- 用户启动研究任务后，Qwen 主 Agent 调度多个专业 Agent 执行周期分析、机制推理、自动实验、假设生成和证据审查。
- 各 Agent 的运行状态、中间产物和实验结果持续回填到当前 Dashboard，而不是跳转到新页面。
- 用户可以在假设工作台中查看证据并提出质疑，系统在反馈迭代区域展示修订前后变化。
- 研究流程结束后，用户继续向下滚动查看报告预览和后续验证计划。

## 9. 自我校正机制

自我校正是本项目区别于普通预测系统的关键能力。

系统需要显式记录以下信息：

- 触发条件。
- 证据或失败原因。
- 被修改的实验或假设。
- 新结果。
- 置信度变化。

示例：

- 如果某个模型只有在包含 F10.7 时表现良好，则自动运行去除 F10.7 的特征消融实验。
- 如果某个假设只被最近几个周期支持，但被更早周期反驳，则降低该假设置信度，并标记其周期依赖性。
- 如果系统检测到跨周期关系漂移，则生成新的非平稳性假设。
- 如果极区磁场数据缺失，则切换到 proxy 特征，并把证据质量标记为较低。
- 如果本轮实验结果与 LLM Wiki 中某条 canonical 知识矛盾，则触发知识冲突审查，由主智能体裁决是降级相关假设、还是把矛盾作为新反例以 candidate 身份写回知识库。
- 如果某条假设依赖的 canonical 知识条目因数据校正被标记为 deprecated，则重新评估该假设置信度，必要时进入下一轮修正。

## 12. 成功标准

项目达到以下标准即可支撑竞赛提交：

- 评委可以调用公开 API，并获得结构化研究输出。
- 评委可以打开前端并运行至少一个完整研究任务。
- 系统能展示真实或给定太阳活动数据。
- 系统能展示模型预测结果和评估指标。
- 系统能展示科学假设、证据链和反证条件。
- 系统能展示至少一条自我校正或实验迭代日志。
- 系统能导出可检查的研究报告。

## 13. 推荐开发节奏

两个月投入时间建议分为四个阶段：

### 阶段一：数据和基线实验

目标：

- 完成数据下载、清洗、周期切分和特征表。
- 实现基础预测实验和回测。
- 预置初始领域知识库 seed（太阳物理核心概念、主流发电机机制、数据源说明等 canonical 条目）。

产出：

- 数据处理脚本。
- 特征表。
- 基线实验结果。
- LLM Wiki 初始 seed 知识库（含来源与置信度标注）。

### 阶段二：Agent 编排和证据结构

目标：

- 搭建“统一主 Agent + 六个子 Agent（含知识管理子Agent）”的 Pi Agent 工作流，并接入横向 LLM Wiki 知识基础设施。
- 定义假设 schema、实验日志 schema、证据评分 schema 和知识条目 schema。
- 实现假设生成和证据审查流程，以及知识检索/候选写回/晋升废弃生命周期。

产出：

- 主 Agent 调度流程和子 Agent 分工说明。
- 候选假设生成样例。
- 证据评分样例。
- 知识管理子Agent 与 LLM Wiki 检索、写回、溯源样例。

### 阶段三：API 和前端

目标：

- 实现可调用测试 API。
- 实现交互式前端页面。
- 打通一次完整研究任务。

产出：

- API 文档。
- 前端演示入口。
- 代表性测试案例。

### 阶段四：竞赛材料打磨

目标：

- 完成技术报告、PPT/PDF 和演示视频。
- 补充可复现实验结果。
- 优化展示叙事。

产出：

- 不超过 20 页的 PPT/PDF。
- 技术报告。
- 源码仓库。
- 10 分钟内演示视频。

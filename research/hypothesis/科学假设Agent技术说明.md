# 科学假设 Agent 1.0 技术说明

## 产品定位

科学假设 Agent 1.0 负责基于研究问题、已有证据、研究规划和真实实验结果形成、审查、比较与更新科学假设。它与研究规划 Agent、自动实验 Agent 是三个独立产品：本 Agent 不制定研究路线，也不执行实验；上游两个产品的输出对本 Agent 而言只是可选的输入材料。

非目标：不运行实验、不生成实验数据、不把一次假设组合升级为科学定论、不为满足固定数量生成重复候选。

## 运行架构

只在 Pi 中运行，Pi 负责 Qwen 模型（`dashscope/qwen3.7-max-2026-06-08`，`high` 推理等级）、Prompt、Skills、Tools、会话状态和交互。系统由六个 Pi Tools 和八个可组合 Skills 构成。Python 确定性核心只是 Pi Tools 的实现层，不是独立入口；绕过 Pi 直接运行 `run_hypothesis.py` 会被拒绝。

```text
用户 → /scientific-hypothesis → Pi Agent（Qwen）
        ├─ scientific_hypothesis_bind_request      绑定请求，返回响应合同与科学边界
        ├─ scientific_hypothesis_inspect_upstream  读取并核验自动实验 run（哈希+终态门）
        ├─ scientific_hypothesis_bind_evidence     逐条绑定并核验上游证据（0–20 条）
        ├─ scientific_hypothesis_validate_response 一次性结构+科学语义检查
        ├─ scientific_hypothesis_rank              rubric 七维排序检查（可追溯理由+锚点）
        └─ scientific_hypothesis_freeze            无参保存，写三份文件并回读核验
```

每个工具调用都是扩展（`.pi/extensions/scientific-hypothesis/index.ts`）向 `run_hypothesis.py` 桥接进程发起的一次有界调用：标准输入输出 JSON、60 秒超时、输出上限 512 KiB、只允许在项目目录内运行。桥接无状态：证据登记簿随每次调用的载荷传递，权威副本保存在 Pi 会话状态中，跨会话中断后可恢复。

## 模型判断与确定性门禁分工

模型负责：判断是否就绪/澄清/阻塞；形成机制上可区分的候选；机制、预测、替代解释与混杂因素的科学内容；逐项说明对象、时空、数据、方法、成立条件、失效条件和外推限制；区分探索性假设、基于证据的机制推断与实证支持等级；说明不确定性来源、推断影响与降低方案；判断证据与候选的关系；给出定性置信度与理由、下一项检验的区分力及证据更新说明。

确定性程序负责：

- 请求绑定、封闭字段、枚举与交叉引用检查。
- 证据角色门：`verified_support=false` 的内容只能以 `gap` 登记，不得用作支持或反对。
- 实验证据门：`experiment_summary` 只允许出现在实验执行记录材料上；技术失败记录不得携带指标；已完成执行必须携带原始指标；未完成执行只能标记技术失败。
- 引用闭合：所有证据引用必须指向登记簿；预测与下一项检验的候选引用必须存在；下一项检验区分多个候选时必须包含本候选。
- 去重：候选陈述不得逐字重复；多候选时机制摘要不得完全相同；每个候选必须出现在区分说明中。
- 置信度一致：无支持证据或存在已核验反对证据时不得为 high；置信度理由不得写精确百分比。
- 数据覆盖范围门：候选陈述或适用范围的泛化越出所绑定材料的已知覆盖范围（如 JW-FD 磁图只覆盖 2011 年前后个别活动区）时，置信度不得为 high；该规则写死在合同里，不靠模型自觉。
- 科学边界完整性：每个候选必须分别填写研究对象、时间/阶段、空间、数据口径、方法口径、成立条件、失效条件和外推限制；适用范围摘要不能替代结构化边界。边界条件、必要前提、关键假设、混杂因素和证伪条件是不同概念，不得相互代填。
- 认识论状态一致性：候选主张明确标为探索性或受证据约束；机制明确标为基于证据的推断、探索性推断或未知；`empirical_support=verified/partial` 必须存在已绑定的非 Wiki 实证支持。Wiki 只可约束机制和范围。
- 不确定性完整性：每个候选必须列出测量、抽样、模型形式或可迁移性不确定性，并说明其对推断的影响和降低方案。
- 表述边界：不得声称“首次提出”；证伪条件与检验信号中的数值门槛必须能追溯到已绑定证据或请求原文；没有实证支持时不得写“所有/普遍/任何活动周”等无界泛化；“显著/明显/稳定”等判断词必须绑定预注册判据、误差界/区间和检验方法，否则改写为方向明确的结果。
- 排序核验：每条名次必须附可追溯理由与关键证据锚点（锚点必须指向该候选自身的已核验支持证据）；名次为从 1 开始的连续整数并覆盖全部候选；名次与成对判断的偏好方向一致。排序分数由代码按权重确定性重算。
- 保存门禁：只有通过检查的响应才能保存；保存时重新生成 id、时间戳与哈希，写盘后立即回读复核，任何失败整体回滚。

## 上游交接通道

`inspect_upstream` 读取自动实验 Agent `runs/<run_id>/` 的公开产物（`entry_result.json`、`record.json`、`report.md`、`audit.md`、`public/`），由代码核验 record/report/audit 三项 sha256、`run_id` 一致性、`status=finalized` 与科学终态。只有 `completed_*` 终态且全部哈希一致的产物返回 `verified` 并附证据摘要（结论、数据范围、声明边界、报告摘录）；其余情况一律返回 `blocked`，该产物只能列为证据缺口。`record.json` 的 `input_snapshot` 中若含研究规划反馈（规划 Agent 已冻结，其产出只能经此链路透入），一并登记为上游证据来源。队友数据与特征 Agent 的契约本轮不兼容，仅在材料枚举中保留 `data_feature` 入口。

## 合同

公共合同统一使用 `scientific-hypothesis-*-v1` 前缀，共六份（`specs/`）：

| 合同 | 作用 |
| --- | --- |
| `hypothesis_request_v1` | 用户请求：研究问题、零到多份上游材料、零到多条已有假设、候选上限 |
| `hypothesis_response_v1` | Agent 响应：`hypotheses_ready`、`clarification_needed`、`hypothesis_blocked` 三选一 |
| `hypothesis_ranking_v1` | 初步排序：rubric 七维等级、名次+理由+证据锚点、成对判断 |
| `upstream_inspection_v1` | 上游自动实验产物核验结果：`verified` 或 `blocked` |
| `hypothesis_portfolio_v1` | 正式组合：冻结后的候选、区分说明、排序、反例/冲突点区块、证据登记簿与哈希 |
| `hypothesis_outcome_v1` | Pi 入口终态结果：任何终态都带面向用户的 Markdown |

候选假设单元包含：主张与适用范围摘要；结构化边界条件（研究对象、时间、空间、数据、方法、成立条件、失效条件、外推限制）；认识论状态（主张、机制、实证支持及依据）；机制（摘要、依据、必要前提）；关键假设；可观测预测（区别于谁、什么结果会削弱它）；支持证据、反对证据与证据缺口；替代解释、混杂因素和可证伪条件；不确定性来源、影响与降低方案；下一项检验、定性置信度、证据更新说明与已有假设谱系指针。

## 机器记录与用户报告分离

`hypothesis_portfolio.json` 保存精确机器事实（id、哈希、证据登记簿、排序、反例/冲突点区块）；`hypotheses.md` 由确定性渲染器从组合生成，只使用自然科研语言，不出现 schema 名、字段名、枚举、证据 id、检查轮次或保存机制。每个候选在报告中单独展示边界条件、认识论状态和不确定性，不能为压缩篇幅而省略。证据在报告中以“实验结果（材料名）”等自然名称出现。反例/冲突点区块由代码从各候选的反对证据与证据缺口自动汇总，排序节由名次、理由与证据锚点组成。

## 失败与中断处理

- 检查一次列出全部可发现问题；模型保留已正确内容一次性修正，修正次数不设固定截断点。
- 澄清与阻塞响应只检查不保存，直接向用户呈现自然语言问题或原因。
- 模型中途用文字结束回合时，扩展自动续跑并提示最近检查结果；请求、证据登记簿、检查次数和最近错误持久化在 Pi 会话条目中，重启后从原任务继续。
- 未成功保存前不向用户展示内部错误或候选草稿；任何终态都有正式交付物。

## 与前两个 Agent 的关系

工程骨架（Pi 单一入口、自然语言命令、空命令输入框、双视图、会话续接、一次汇总检查、无参保存）复用自研究规划 Agent 1.0 的验证结果；科学内核（证据角色门、候选去重、可证伪性、置信度纪律、证据更新谱系、数据覆盖范围门、排序核验）按假设推理的特点重新设计。自动实验 Agent 的实验记录是本 Agent 最可靠的证据来源，经上一节所述 `inspect_upstream` 通道核验后进入证据绑定。
